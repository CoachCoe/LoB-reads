### BLOCK-1 (FLOW-1 / ORG-7 / DEAD-12) — `/my-books` ships Prisma to the browser and never hydrates
- **file:line** `src/app/(main)/my-books/ShelfSection.tsx:3`; `src/server/catalog.ts:387`
- **severity** blocker
- **violates** `STATUS.md` Lesson 7 — "A green build is not a working container… Anything resolved at runtime by detection has to be exercised at runtime." Also `README.md:206` / `ARCHITECTURE.md:52` ("All database access lives here, never in a route").
- **verified by the main thread**, at every link:
  1. `ShelfSection.tsx:3` — `import { coverUrl } from "@/server/catalog"` — a **value** import, in a `"use client"` file. (Every other client import from `@/server/*` is `import type`, which is erased; this is the only offender.)
  2. `src/server/catalog.ts:1` imports `prisma`; `:387` evaluates
     `export const SEARCH_SQL_MARKER = Prisma.sql\`catalog.works\`` at **module scope**.
  3. The built client chunk `.next/static/chunks/1hl_oz86brcst.js` contains
     `globalThis.prisma??new r.PrismaClient({log:["error"]}),r.Prisma.sql\`catalog.works\``
     **and** `"Remove from shelf"` (i.e. `ShelfSection`).
  4. `grep -rl "1hl_oz86brcst" .next/server` → exactly one file,
     `.next/server/app/(main)/my-books/page_client-reference-manifest.js`. The chunk
     belongs to `/my-books` and to no other route.
  5. `node_modules/.prisma/client/index-browser.js:63-66` —
     `Prisma.sql = () => { throw new Error("sqltag is unable to run in this browser environment…") }`.
- **effect** Loading `/my-books` throws synchronously during client module
  evaluation. The server HTML renders, then hydration dies before `ShelfSection`
  is defined, so the shelf grid's remove buttons are inert. Journey A does not
  survive hydration. Nothing in the suite or the build detects it.
- **fix** Move `coverUrl` to a client-safe `src/lib/covers.ts`; re-export from
  `catalog.ts` for existing server callers; import from `@/lib/covers` in
  `ShelfSection.tsx`. Delete `SEARCH_SQL_MARKER` (dead — see DEAD-12). Add
  `import "server-only"` to `src/server/catalog.ts` so a future value import
  fails the build. Add a conventions test forbidding a `"use client"` file from
  value-importing `@/server/*` or `@/lib/prisma`.

### BLOCK-2 (ORG-1) — CI cannot pass: `deploy:verify` rejects CI's own secret
- **file:line** `.github/workflows/ci.yml:98` ↔ `scripts/deploy/verify.ts:94-101`
- **severity** blocker
- **violates** `PRD.md:110-114` — the release gate "exits non-zero, so it gates a
  release rather than being a checklist someone reads." A gate that cannot pass
  gates nothing.
- **verified by the main thread**: CI sets
  `NEXTAUTH_SECRET: ${{ github.sha }}-not-a-placeholder`. `verify.ts:96` rejects
  `/placeholder|changeme|secret-not-for-deployment/i`. The string
  `"…-not-a-placeholder"` **contains** `placeholder`:
  `node -e '/placeholder/i.test("abc-not-a-placeholder")'` → `true`.
  `fatal` defaults true (`verify.ts:46`) → `process.exit(1)` (`:370`) → the
  `check` job fails.
- **why it was never noticed** CI runs on `pull_request` and `push: [main]`. No
  PR has ever been opened, and `main` is 53 commits behind. This step has
  probably never executed.
- **fix** The audit's hard rules forbid editing CI workflows, so the fix goes to
  the root cause in `verify.ts`: match placeholder *values*, not substrings —
  compare the secret against an exact set of known placeholders, and add a
  minimum-length check. A one-word change in `ci.yml` would also fix it and is
  noted for the reviewer, but is out of bounds for this audit.

# SECURITY

### SEC-1 — Rate limiter is quadratic and its prune cannot reclaim what an attacker creates
- **file:line** `src/lib/rate-limit.ts:70-76` (with `:50-52`, `:100`)
- **severity** major
- **violates** A defence must not be the cheapest way to attack what it defends.
- **evidence (measured by the agent, code path re-verified by the main thread)**
  Once `buckets.size > 10_000`, **every** `checkLimit` iterates the whole map,
  and a bucket is deleted only when *all* its timestamps have aged out — with
  `LIMITS.register`'s 1-hour window, a fresh bucket is unprunable for an hour.
  Measured with distinct keys through `LIMITS.register`:
  9,000 keys → 10 ms; +5,000 (map ~15k) → 795 ms; +5,000 (~20k) → 1,167 ms;
  +5,000 (~25k) → 1,999 ms. The first key still had `remaining: 3` after 25,000
  more, confirming nothing was reclaimed.
- **attack** `POST /api/auth/register` with body `{}` and a rotating
  `X-Forwarded-For`. The bucket is created at `route.ts:13` *before* the body is
  parsed, so an invalid body still costs a bucket. After 10,000 requests every
  later `checkLimit` — including every sign-in — scans the map. No account and no
  valid body required.
- **fix** Replace the scan with O(1) amortised insertion-order eviction:
  `while (buckets.size > MAX_BUCKETS) buckets.delete(buckets.keys().next().value)`,
  plus `buckets.delete(key)` before `buckets.set(key, hits)` so a live bucket
  moves to the back instead of being evicted as stale.

### SEC-2 — `X-Forwarded-For` trusted verbatim; both IP-keyed limits are bypassable
- **file:line** `src/lib/rate-limit.ts:90-96`; `src/lib/auth/options.ts:32-44`
- **severity** major
- **violates** A forwarding header is client data until a trusted proxy wrote the
  element you read. Both sites take the **leftmost** entry — exactly the part the
  client controls. A proxy *appends*.
- **attack** Registration flood: `LIMITS.register` (5/hour) becomes 5 × (spoofed
  values) = unbounded. Credential stuffing: `login:email:*` still caps one
  account at 10/15min, but `login:ip:*` — whose whole purpose is to stop one host
  guessing across many accounts — is defeated by rotating the header.
- **fix** Read the rightmost-untrusted hop with a configured trusted-hop count,
  and have `options.ts` call `getClientIp` instead of re-deriving it, so there is
  one implementation.

### SEC-3 — Request bodies fully buffered before any size check
- **file:line** `src/app/api/import/goodreads/route.ts:33` vs `:47`;
  `src/app/api/users/[userId]/avatar/route.ts:36` vs `:52`;
  `src/app/api/fictional-worlds/[worldId]/upload/route.ts:39` vs `:59`
- **severity** major
- **violates** A size limit enforced after the bytes are in memory is not a limit.
- **evidence** `formData()` is awaited before the `file.size` check in all three.
  There is no other cap: `serverActions.bodySizeLimit` applies only to Server
  Actions (confirmed in `node_modules/next/dist/docs/`), there is no
  `middleware.ts`, and `next.config.ts` sets none. Next is 16.3.1.
- **attack** `POST /api/import/goodreads` streaming a 4 GB part. **That route has
  no rate limit at all**, so requests can be issued concurrently until OOM.
- **fix** Reject on `content-length` before touching the body in all three, and
  add a `checkLimit` to the import route (see SEC-4).

### SEC-4 — Goodreads import runs 2,000 trigram matches and their writes synchronously, unrated
- **file:line** `src/app/api/import/goodreads/route.ts:72-74` →
  `src/server/imports.ts:109,141-176,185-210`
- **severity** major
- **violates** Unbounded per-request work behind no quota is a DoS primitive.
- **evidence** `createImportSession` calls `matchSession`, which per row may run
  `findWorkKeyByTitleAuthor`, then `findCandidates` (a `similarity()` trigram
  scan over `catalog.works`, ~40 ms against the real catalog), then `applyRow`
  (up to three further write paths, two of them transactions). `MAX_ROWS = 2_000`
  bounds the loop, not the cost. No `checkLimit` on the route.
- **attack** One 2,000-row CSV of random titles (forcing the expensive branch on
  every row) × 50 concurrent requests exhausts the Prisma pool; every other page
  times out.
- **fix** Add the per-account `checkLimit` the other two upload routes already
  have, and have `createImportSession` persist rows and return without calling
  `matchSession` (which is already documented as safe to re-run).

### SEC-5 — `isModerator` is frozen into a rolling 30-day JWT; there is no revocation
- **file:line** `src/lib/auth/options.ts:77-98`
- **severity** major
- **violates** Authorization state must be revocable.
- **evidence** `jwt({ token, user })` sets `token.isModerator` only when `user` is
  present, i.e. only at sign-in. `session: { strategy: "jwt" }` sets no `maxAge`,
  so NextAuth's 30-day default applies (`node_modules/next-auth/core/init.js:45`)
  and v4 re-encodes with a fresh expiry on each session read — for an active
  user the token never expires and the flag is never re-read. `getCurrentUser`
  returns `session?.user` straight from the token; no query is involved.
- **attack** Demote a moderator in the database; their existing cookie still
  passes `map.addedById !== user.id && !user.isModerator`
  (`fictional-worlds/maps/[mapId]/route.ts:31`) and still deletes anyone's map
  **and its blob** — indefinitely. Same cause: a deleted account's cookie still
  authenticates, and *promoting* a moderator does nothing until re-login.
- **fix** Set `session.maxAge`, and re-read `isModerator` in the `jwt` callback on
  a bounded interval (one query per active session per few minutes).

### SEC-6 — Every anonymous work-page view performs a database write
- **file:line** `src/app/(main)/work/[olKey]/page.tsx:61` →
  `src/server/enrichment.ts:30-45`
- **severity** major
- **violates** An unauthenticated read path should not be a write path whose
  volume the reader chooses.
- **evidence** `enqueue` is an upsert. The page is unauthenticated and
  dynamically rendered per request; there is no rate limit on page renders.
- **attack** Walk sequential public Open Library keys (`/work/OL1W`, `OL2W`, …).
  Each key lacking a description inserts a queue row. `claimJobs` orders by
  `created_at` (`enrichment.ts:80`), so the junk drains **ahead of** genuinely
  popular works — destroying the prioritisation `backfill.ts` and PRD R4 exist
  for. Worker rate is 5/s.
- **fix** Gate the enqueue on a signed-in session, drop the `await`
  (fire-and-forget), and ideally require `editionCount > 1`.

### SEC-7 (with FLOW-12) — No moderator delete path for locations; orphaned pins are undeletable

### SEC-10 — Cover fetcher persists a remote-supplied `Content-Type` under year-long immutable caching
- **file:line** `scripts/enrich/covers.ts:109-111` →
  `src/lib/storage/objects.ts:111-118`
- **severity** minor
- **evidence** The upload routes validate type and magic bytes; the cover fetcher

### SEC-11 — `deploy:verify` accepts an `http://` `NEXTAUTH_URL`

### SEC-13 (canonical: KNOWN-2) — `avatarUrl` accepts `javascript:` and `data:` URLs

### SEC-14 — LIKE metacharacters unescaped in the import's auto-apply author match
- **file:line** `src/server/catalog.ts:495-505`
- **severity** major — agent filed as minor; raised because this is the
  **auto-apply** path, not the review queue
- **violates** Parameterisation stops SQL injection, not pattern-metacharacter
  injection into `LIKE`.
- **verified by the main thread** `author` is bound safely but its `%`/`_` remain
  pattern operators, so `author = "%"` makes the predicate
  `LIKE '%%%'` — matching every row, switching off the author half of the match.
  `imports.ts:144` feeds the result straight to `applyRow` and marks the row
  `status: "matched"`, `matchedBy: "title_author"`, with **no review**.
- **attack** A CSV row whose `Title` is a real catalog title and `Author` is `%`
  silently attaches to whichever work with that title has the highest
  `edition_count` — shelved, rated and marked read without review. Reachable
  whenever someone imports a CSV they did not author.
- **fix** Escape `\`, `%`, `_` before binding; Postgres's default `LIKE` escape
  is `\`, so no clause change is needed.

### SEC-15 — Upstream `Retry-After` trusted without a ceiling
- **file:line** `src/lib/sources/enrichment.ts:82-89` →
  `src/server/enrichment.ts:159-169`
- **severity** minor
- **evidence** The computed backoff is capped at 3600 s; the supplied path
  (`retryAfterSeconds ?? …`) bypasses the cap entirely.
  `Retry-After: 999999999` schedules a retry ~31 years out. `claimJobs` filters
  `next_attempt_at <= now()`, and `reclaimStale` only rescues `running` rows, so
  the job is stranded `pending` forever and the queue silently stops producing.
- **fix** `Math.min(3600, retryAfterSeconds ?? computed)`.

### SEC-16 (with DEAD-9) — Ten `getServerSession` routes guard on `session.user` then use `session.user.id`
- **file:line** ten files, incl. `api/progress/route.ts:16,31`,
  `api/shelves/route.ts:11,26`, `api/users/[userId]/follow/route.ts:13,32,51`
- **severity** minor
- **evidence** The nine `getCurrentUser` routes assert `!user?.id` — the field
  they use. The ten `getServerSession` routes assert `!session?.user` and then

# OPEN QUESTIONS — product decisions, not resolved by guessing

**OQ-1.** Does `PRD.md:151`'s prohibition ("nothing derived from it is served")
cover the derived aggregate tables, or only redistribution of the corpus itself?
`ARCHITECTURE.md:236-241` reasons about *redistribution* under ShareAlike, which
is a narrower claim. SPEC-1 is written against the literal reading. If only
redistribution is meant, the fix is UI attribution rather than a runtime gate — a
materially different change.

**OQ-2.** **R3 and §5 appear to conflict.** R3's "Done when: a reader landing on
a mainstream book sees a rating and neighbours more often than not" can only be
met today by the goodbooks-10k graph, which §5 forbids serving. R3 offers "a
larger corpus, or real user ratings, or both" without saying whether a
differently-licensed corpus is a precondition.

**OQ-3.** **R1's own open question is still open** (`PRD.md:69-70`): are
approximate results acceptable for very common words? No code decision has been
taken; `searchWorks` still ranks the full match set, `COUNT_CEILING` bounds only
the count, and the plan assertion R1 requires does not exist.

**OQ-4.** **Is `/map` intended to be public?** `PRD.md:33-34` guarantees no login
wall "to look at a book or a public shelf" — the map is neither, and R6 does not
say. It renders only community-contributed data. This decides FLOW-2 and changes
the shape of the R6 work.

**OQ-5.** **R4's "the works people actually open"** has no definition and no
measurement: `PRD.md:165-167` states nothing is instrumented. Whether "popular
head" means `edition_count` order, `work_rating_stats` order, or observed traffic
changes what `enrich:covers` should queue.

**OQ-6.** **SEC-12, registration enumeration** — closing it costs the "this email
is already registered" message, which is real UX. There is no email verification
in the app, so the pragmatic alternative is to accept the trade-off and rely on
SEC-2's fix. Needs a decision.

**OQ-7.** **DEAD-4 / DEAD-1 / BLOCK-4** — is there meant to be a public HTTP API?
Six read handlers have no in-app caller but five are documented in `README.md`.
If the API is a product, they stay and need tests; if not, they and their README
lines go. The same question decides whether `POST /api/shelves` and
`POST /api/fictional-worlds` get UI or get removed.

**OQ-8.** **SPEC-7** — which table owns work↔world association,
`app.work_fictional_worlds` (counted, never written) or `app.work_locations`
(written, not counted)?
