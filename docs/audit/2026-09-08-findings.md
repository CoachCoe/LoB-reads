# BLOCKERS

## RUN-1 / JR-6 — "Finish" is not idempotent: each click logs another book read

`src/server/progress.ts:204-226`, `:228-246`; `src/server/wrapped.ts:87`

`finishReading` looks for an *open* session. Finding none it calls
`startAndFinish`, which creates a new already-finished session. The partial
unique index constrains open sessions only:

    reading_sessions_one_open_per_work UNIQUE ("userId", work_key) WHERE (finished_at IS NULL)

so finished sessions are unbounded. Measured: five POSTs of
`{"action":"finish"}` for one work produced five finished sessions, each with
`started_at == finished_at`. `wrapped.ts:87` is
`booksRead = finishedBooks.length` — sessions, not distinct works. So
`/wrapped/projections` rendered, for ONE 176-page book read once:

    5 Books Read · 880 Pages Read · 0.6 Books/Month · "you'll read 7 books by year end"

Two passes found this independently: by double-clicking Finish (RUN-1) and by
re-uploading a Goodreads CSV (JR-6), which re-applies every row and calls
`finishReading` again for each. `__tests__/integration/goodreads-import.test.ts`
has 34 tests and no idempotency case.

This is the same double-counting `progress.ts:70-78` says was fixed for the
*start* path: "quietly undoing the finish and double-counting it in
getReadingStats and /wrapped." The start path was fixed; the finish path was not.

Violates PRD R0 (the reading loop) and PRD §2 ("wants to see what they read
this year").

**Fix.** In `finishReading`, when there is no open session, look for an existing
finished session for that work with the same `finishedAt` **date** and update it
rather than inserting. Re-reads stay supported through the explicit
`start` → `finish` pair the UI already offers after a finish. The test must
assert the session **count**, not the response status.

## RUN-3 / SPEC-2 / JB-3 — Both search gates are blind to the failure mode R1's design introduced

`scripts/dev/bench-search.ts:133-148`; `scripts/deploy/verify.ts:463-475`

R1's "Done when" is "the bound is held by something that fails when it breaks"
(PRD:119-121). The R1 fix bounds two arms with a `statement_timeout` whose
documented behaviour is to "fail safe — the reader gets no results". An
abandoned arm is therefore **fast and empty**.

`bench-search.ts` computes `rows` (`:134`), prints it (`:143`), and never
asserts on it: `failures` is populated only by `searchMax > BUDGET_MS` (`:138`,
`:146`). A regression that converts a working query into a timed-out empty one
*lowers* the measured time and makes the gate greener.

`verify.ts` has the same blind spot: `search responds for "q"` asserts
`status === 200` (`:467`), `search is under a second` asserts the clock (`:472`).
A 200 rendering "Nothing matched" passes both.

Demonstrated: in one session, `/search?q=the+hobbitt` returned zero results on
3 of 12 consecutive requests, and `npm run bench:search -- --gate` exited **0**
and printed "All 22 queries within the 1000ms warm budget."

This is the "assertion that cannot fail" class the testing skill says has
shipped four blockers past a green suite.

**Fix.** Record an expected minimum row count per query in `bench-search.ts` and
fail the gate when a query that should answer returns nothing. Add the same
assertion to `verify.ts` for `dune`, `fiction` and `mockingbrd`.

## RUN-2 / SPEC-4 / JB-4 — The 700 ms fuzzy budget does not clear the query it was calibrated on

`src/server/catalog.ts:283-289`, `:298-300`

`catalog.ts:283-289` states the criterion: "The slowest legitimate typo in the
benchmark is 'the hobbitt' — 76,457 index candidates for 20 matches, about
590ms for the whole page — so the budget has to clear that … 700ms keeps ~150ms
of headroom." PRD R1's table records this query as "20 results, 565ms".

Measured warm on the real catalog, `searchWorksFuzzySql` for `the hobbitt`:

| | p50 | max |
|---|---|---|
| `limit: 24` | 606 ms | **857 ms** |
| `limit: COUNT_CEILING` | 598 ms | **708 ms** |

A third pass measured 12 runs at 634-699 ms with excursions to 867, 2,038 and
3,307 ms. The p50 matches the recorded 590 ms; the tail does not. The stated
"~150ms of headroom" is negative at the tail, so the cutoff lands inside this
query's own latency distribution — which is why `/search?q=the+hobbitt` is
non-deterministic (20 results or "Nothing matched", 25% empty in a 12-run
sample).

The larger `limit` is **not** the cause: limit=24 and limit=1000 cost the same.

**Fix.** Land RUN-3's recall assertion first, so the budget is guarded, then set
the budget from the measured tail rather than the p50. The module's own note
sanctions "anything between roughly 600ms and 900ms"; the full-text count arm is
5-25 ms, so 900 ms keeps R1's one-second budget.

## SEC-1 — `deploy:verify`'s two secret gates both pass a known placeholder

`scripts/deploy/verify.ts:103-120`

The value in the developer's `.env` is `your-secret-key-change-in-production`
— **36 characters**, and published in this repo's own history
(`bookshelf/README.md` at `3847ecd`, removed in `c128cfe`, so still in history;
confirmed with `git log --all -S`).

Both gates pass it, verified arithmetically:

- `:117-120` requires `secret.length >= 32` → 36 ≥ 32, **passes**
- `:103-113` compares against six exact placeholder strings (`changeme`,
  `ci-placeholder-secret`, `ci-secret`, `placeholder`, `secret`,
  `secret-not-for-deployment`) → not among them, **passes**

The 2026-08-31 remediation deliberately replaced substring matching with
exact-value matching "and let length carry the real protection". This
placeholder is long, so neither half catches it. NextAuth v4 imposes no entropy
requirement of its own (`src/lib/auth/options.ts:183`).

With the secret known, a JWT can be minted with any `token.id` and
`isModerator: true`; the five-minute revalidation (`options.ts:142-163`)
re-reads `isModerator` for an id that exists, so a forged token naming a real
user is refreshed *into* that user's privileges. The gate's own hint says
"every session token is forgeable with a known secret."

`.env.example:32` correctly ships blank, so the value exists only in the
developer's `.env` and in history — which is the copy that gets carried forward.

**Fix.** Add this exact string to `KNOWN_PLACEHOLDERS`. Rotating the local
secret and considering a 44-character floor are recorded under "Needs action
outside the repo" and "Needs a decision".

## DEAD-1 / JC-1 — The wiki *edit* half is built server-side and no UI reaches it

`src/app/api/works/[workKey]/locations/route.ts:97`;
`src/app/api/authors/[authorName]/locations/route.ts:106`

PRD §2: "Editing is wiki-style — **anyone signed in may edit**, uploader-or-
moderator may delete — because the data only exists if contributing is easy."

The edit path exists at every layer below the UI: both routes export `PATCH`

(`src/server/work-locations.ts:154`), `updateAuthorLocation`
(`src/server/authors.ts:218`); `updateWorkLocationSchema` /
`updateAuthorLocationSchema` (`src/lib/http/schemas.ts:199`, `:206`); and a

Nothing calls it. Verified mechanically: the only client `method: "PATCH"` in
the app is `FictionalWorldsPanel.tsx:149` (map metadata) and
`SettingsForm.tsx:71` (profile). `LocationRow.tsx:18` exposes `onDelete` as its
only mutation prop; `useCrowdsourcedLocations.ts:115-124` returns
`addLocation`, `removeLocation`, `refresh` and nothing else.

**Verified by running that the server half works correctly:** user B (not the
uploader) PATCHed user A's location → 200, `updated_by_id` written with B's id
and `added_by_id` unchanged; user B DELETEd the same location → 403 "You can

exactly as the PRD states — it simply cannot be exercised from the product.

`git show --stat eb0d12a` ("Let anyone signed in correct a location, as the rule
says") touched PRD, README, STATUS, one test, the migration, two schemas, two
routes, two server modules — **zero components**.

working API routes with no UI to reach them." Both of those (custom shelves,

**Fix.** An edit control on `LocationRow` mirroring `onDelete` but gated on

issuing `PATCH ${basePath}?locationId=…`; both sections reusing their existing

feature work, so it is recorded rather than fixed in this round — and see OQ-1,
because the alternative reading makes it dead code to revert instead.

## DEAD-3 — The `name_norm` rule is copied into the ingest, where no test runs

`scripts/ingest/03-normalize.sql:127` vs
`prisma/migrations/20260901220000_author_name_norm/migration.sql:37-43`

The trigger computes `lower(unaccent(coalesce(NEW.name, '')))`.

Those tests caught it because the search vector is a **trigger** the test
database carries. The ingest's inline copy is in a `.sql` file the test database
never runs, so the equivalent regression is invisible.
`scripts/deploy/verify.ts:288-290` checks only that the trigger *exists*, not
what it computes, and has no check for `authors_name_norm_trigger` at all.

## Security

**RUN-7 / SEC-7 — The multipart size gate is bypassable with chunked encoding.**
`src/app/api/users/[userId]/avatar/route.ts:48-52`;
`fictional-worlds/[worldId]/upload/route.ts:50-54`;
`import/goodreads/route.ts:58-62`; contrast `src/lib/http/api.ts:101-128`.

The security pass reported this reasoned-but-unverified. **Verified by running,**
authenticated, 12,582,920-byte payload against `MAX_FILE_SIZE = 5MB`:

| request | result |
|---|---|
| with `Content-Length` | **413** "File too large. Maximum size is 5MB." |
| `Transfer-Encoding: chunked`, no `Content-Length` | **503** "Uploads are not available right now." |

The 503 is the tell: `declaredBodyTooLarge` did not fire, `formData()` buffered
all 12 MB, and execution reached `isStorageConfigured()`. `api.ts:95-99` states
the principle — "Content-Length is advisory and absent on a chunked request …
this is the one that actually holds" — and only the JSON half got the byte-
counting bound. The remaining bound is `LIMITS.upload`: 20 requests per account
per hour, each able to buffer arbitrary bytes.
**Fix.** Read `request.body` through a length-counting reader that `cancel()`s
past the cap, then build the `FormData` from the bounded buffer. `readBounded`
is the right shape and needs a `Uint8Array` variant.

**SEC-3 — `POST /api/reviews` is unrated and feeds the public home page.**
`src/app/api/reviews/route.ts:9` (verified: no `checkLimit` anywhere in the
file) → `src/server/reviews.ts:103-111` → `src/app/(main)/page.tsx:16`.
`HomePage` is public and renders `getRecentReviews(6)` — the six newest reviews
site-wide, `createdAt desc`, no moderation and no per-account share. One account
can hold up to 6.9M distinct review rows of 10,000 characters each, so a loop
over popular work keys owns all six home-page slots indefinitely. The three
location/world routes got `LIMITS.contribute` for this exact shape in the
2026-09-01 round; reviews were never in that inventory.
**Fix.** `LIMITS.contribute` keyed `contribute:review:${user.id}` with the
arrival-and-refund ordering already at `works/[workKey]/locations/route.ts:44-51`.
Separately, bound the home-page module by distinct author.

**SEC-5 — The community-edit `PATCH` on maps is the one unrated wiki write.**
`src/app/api/fictional-worlds/maps/[mapId]/route.ts:54-79` (verified: no
`checkLimit` in the file). By deliberate policy there is no ownership check
(correct per PRD §2) — making it the only mutating handler that is both
ownership-free **and** unrated. Both location `PATCH` handlers, added in the same
round for the same PRD clause, carry `LIMITS.contribute`. So one signed-in
account can walk every `mapId` and rewrite every title and description rendered
on the public `/map`, unbounded. The routes' own headers state the rule:
"community-editable without a limit is one account rewriting every record on the
site in a loop."
**Fix.** `checkLimit(\`edit:map:${user.id}\`, LIMITS.contribute)` with the same
refund ordering. The revert path stays deferred.

**SEC-4 — The map-upload route writes unbounded text, and the world list reads every map.**
`fictional-worlds/[worldId]/upload/route.ts:56-57`, `:93-97`;
`src/server/fictional-worlds.ts:31`; the vacuous guard at
`__tests__/conventions.test.ts:543`, `:564`.
`title` and `description` come from `formData.get(...)` with the only check being
`title.trim().length === 0`, then are written verbatim to unbounded `text`
columns — while the sibling edit path enforces `SHORT_TEXT`/`LONG_TEXT`
(`schemas.ts:172-175`). The multipart body's only ceiling is the advisory one
(RUN-7), so one map row can carry ~5 MB of title. The public anonymous
`GET /api/fictional-worlds` then serialises it: `WORLD_LIST_LIMIT = 500` caps the
*worlds*, but `fictionalWorldInclude` selects `maps` with an `orderBy` and **no
`take`**.
The guard that should have caught it passes vacuously: `conventions.test.ts:564`
asserts the function body merely `toContain("take:")`, which the world-level
`take` satisfies while the nested read stays unbounded.
**Fix.** `updateMapSchema.parse({ title, description })` in the upload route;
`take: MAPS_PER_WORLD` in `fictionalWorldInclude`; tighten the convention test to
assert a `take:` inside each nested `include`/`select`, against the named
constant (see TEST-38).

**SEC-6 — Every per-IP limit disappears silently if `TRUSTED_PROXY_HOPS` over-counts, and `register` has no fallback.**
`src/lib/rate-limit.ts:196-222`, `:236-238`;
`src/app/api/auth/register/route.ts:17-29`; gate at `verify.ts:304-332`.
`clientIpFromHeaders` returns `chain[chain.length - hops]` only when
`chain.length >= hops`; otherwise it falls to `x-real-ip` (which Container Apps
does not set) and then `null`. The 2026-09-01 round fixed the *under*-counting
direction; the *over*-counting direction is silent. `deploy:verify` asserts only
`hops > 0` and that the strategy is explicit — neither compares the number to an
observed `X-Forwarded-For`. Consequence: `login:ip:*` is never recorded and
`register` skips its limiter entirely (`register/route.ts:18` — `if (key)`),
leaving **no cap on account creation**. Login retains a per-email fallback;
registration has no equivalent. `clientIdentificationConfigured()`, written to
detect this state, has **zero production callers** (see DEAD-22).
**Fix.** When `forwardedFor` is non-empty but shorter than `hops`, treat it as
misconfiguration and fall back to the last element; give `register` an
email-keyed fallback bucket; call `clientIdentificationConfigured()` at boot.

**OQ-1 — Is the wiki edit rule settled as "anyone signed in may edit"?**

**OQ-2 — Is a zero-result answer for an all-stopword query the intended outcome?**
PRD:124-125 answers the old question with "approximate results for very common
words are acceptable", which reads as rougher results, not none. `?q=the`
currently returns nothing after ~750 ms even though six works are titled exactly
"the" — so the arm built to answer stopword titles cannot answer its two most
common members. Is the accepted behaviour (a) nothing, (b) the exact matches
with a bigger budget or a supporting index, or (c) a fallback to popular works?
Bears on RUN-2's budget choice.

**OQ-3 — Is "Read" the shelf, or "Read" the finished session?**
Blocks JR-5. Making `addWorkToShelf` create a finished session gives Wrapped a
`finishedAt` the reader never stated (today, for a book read in 2009). Counting
shelf membership instead reopens FLOW-24's inconsistency from the other side.
Asking for a date when the reader picks the Read shelf is more UI than an audit
should assume. The PRD says only "wants to see what they read this year".

**OQ-4 — Is the batch rating table meant to be the work page's only rating source?**
Blocks JR-4. PRD §5 records that "serving an aggregate is not redistributing the
corpus" and names `getWorkRating` as where a licence gate *would* go. Folding
live `app.reviews` into the displayed average changes what that gate would cover,
so this is a licence question as much as a product one.

**OQ-5 — What is "the top 1,000 works"?**
Blocks SPEC-5. Measured 55.3% using the app's own popularity ordering. Nothing
defines the M5 acceptance criterion; under `rating_count` order within the corpus
the claim is trivially 100%. The definition has to be written down before the
claim can be called true or false.

**OQ-6 — Is `MAX_ROWS = 2_000` a product decision or a stopgap?**
Blocks JI-3's fix. Goodreads exports routinely exceed it; PRD §2 names getting
the export in as the first reader's first want, and PRD §6 names abandoned rows
as a signal. If 2,000 stays, the banner must say "split the file"; if not, it
needs `rowsConsumed` and a file identity.

**OQ-7 — Cover the masked guards (TEST-24, TEST-25) or delete them?**
The 2026-09-03 round set precedent both ways: unfalsifiable code written that
round was removed; pre-existing defensive code was kept with the gap written
down. Both of these are pre-existing, which argues for recording — but both are
reachable if a future caller skips the schema, and the importer already writes
reading sessions directly.

**OQ-8 — Which pager is correct?** Blocks DEAD-16. `search` caps the display at
50; `shelf` does not.

**OQ-9 — `bookshelf/tmp-prov.ts`: remove or keep?** The charter protects
behaviour not covered by a test; this file has no caller, no importer and no
invocation path, so there is arguably no behaviour to protect — but it is tracked
code and the rule states no exception. Recommendation: remove it, or move it to
`scripts/dev/` with a header saying which question it answered and drop the
`as never`.

**OQ-10 — Rename the camelCase columns, or document the split?** Blocks RUN-4. A
rename with `@map` leaves the Prisma API unchanged but is a migration against a
deployed database.

**OQ-11 — Are duplicate location contributions meant to be prevented, merged, or allowed?**
Blocks JC-6. A unique constraint rejects the second; a merge model credits both
contributors; allowing them needs clustering (JC-9) so the map does not lie about
density. "Wiki-style" arguably implies merging rather than rejecting.

**OQ-12 — Should `bookshelves` be imported into custom shelves?** JI-6 is a
defect only if yes. The parser collects them, `CustomShelves.tsx` now exists to
hold them, and the settings copy promises "shelves" — but no requirement says
import should populate anything but the three exclusive shelves.

**OQ-13 — Is there meant to be a private shelf?** PRD §2 says "a **public**
shelf", implying a non-public one exists, but `Shelf` has no `isPublic` column
and `getShelfById` has no owner check by design. Blocks JR-8/JB-10's fix.

**OQ-14 — Is `infra/main.bicep` the provisioning path, or a design artifact?**
`main.bicep:6-7` calls itself "a reviewable declaration … not a tested artifact",
but `azure.sh:54-97` treats it as executable with a what-if guard. The answer
decides whether DOC-1/2/3 are template bugs or acceptable gaps in a sketch.

**OQ-15 — Was `BASE_URL`'s absence from `deploy.yml` deliberate?** The container
app's FQDN may not be reachable from the runner before Front Door exists. If so,
`DEPLOYMENT.md:457-467` should say the running-app checks are a manual
post-deploy step rather than part of the automated gate.

**OQ-16 — Is there any intended path to becoming a moderator?**
`User.isModerator` gates deletion of others' contributions and is read from the
session with a documented revalidation window, but no route, page or script sets
it. So "uploader-or-moderator may delete" is, deployed, "uploader only, until an
operator runs SQL". Bears on JC-4: with no moderator, a cascaded-away map has no
one who could have deleted it deliberately.

**OQ-17 — Is `cover_id::int` safe above 2³¹?** A probe hit
`22003 integer out of range` at `cover_id = 3000000000`. Open Library cover ids
are eight digits today, so it is unreachable — but `::bigint::text` or a JS-side
`Number()` would be safe at any value. A silent bound worth a decision.

**OQ-18 — Is `number_of_pages = 0` present in the slice?**
`progress.ts:171` guards with `session.pageCount &&` (falsy for 0) while `:178`
uses `!= null` (true for 0), so a session snapshotted with `pageCount: 0` is
finished immediately at page 0 and moved to Read. `core-loop.test.ts:379-397`
covers `null` but not `0`. Either way the two conditions should be spelled the
same.

**OQ-19 — Is `npm run storage:smoke` in CI?** It is not in `ci.yml`. Both
`putObject` and `deleteObjectByUrl` are only ever the mock in tests, so the
Azure client construction path is unexercised anywhere.

**OQ-20 — Which `DEAD-<n>` numbering survives?** Three audits now carry three
independent `DEAD-1..DEAD-22` series with different meanings, and the
2026-09-01 doc already writes "the prior DEAD-11" to disambiguate. Suggest
date-qualified IDs or one monotonic register.
