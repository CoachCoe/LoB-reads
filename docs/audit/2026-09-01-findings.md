## Addendum — DEAD-4 remediation, and a new finding it exposed

### DEAD-5 (new) — `works.title_norm` and `author_names_norm` are not fully normalised
`prisma/migrations/20260817160000_normalized_trigram_columns/migration.sql:32-34`,
`src/server/catalog.ts` (the query side) · **major**

Found while fixing DEAD-4, by a test of the new column failing.

Both columns are computed as `unaccent(lower(x))`. This database runs
**`lc_collate = C`**, under which `lower()` folds only ASCII — it leaves `É`
alone, and `unaccent` then produces a capital `E`. So the "normalised" column is
not normalised:

```
lower('Émile Zola')            -> 'Émile zola'
unaccent(lower('Émile Zola'))  -> 'Emile zola'     <- what is stored
lower(unaccent('Émile Zola'))  -> 'emile zola'     <- correct
```

Measured on the real catalog: `title_norm` for `"Öffentliche Steuerung…"` is
stored as `"Offentliche steuerung…"`. Both sides use the same wrong order, so a
query in the *same casing* still matches — which is why the accented-title test
passes. They diverge the moment the casing differs:

| query | trigram matches | prefix matches |
|---|---|---|
| `"Öffentliche Steuerung und Gest"` | 1 | 1 |
| `"öffentliche steuerung und gest"` | 1 | **0** |

The trigram fallback still finds the work, so nothing looks broken. What is lost
is the `W_PREFIX` **+20 ranking bonus** on the prefix path — so a reader typing
an accented title in lowercase, which is the normal way to type it, gets the
right book ranked as though it were not a prefix match. That is precisely the
defect the ranking weights exist to prevent.

**Fix:** `lower(unaccent(x))` in the trigger, the same in the query side, then a
backfill of both columns across 6.9M rows and a rebuild of the two GIN trigram
indexes. `03-normalize.sql` needs the same change or the next monthly ingest
undoes it.

**Why not bundled with DEAD-4:** it is a heavy migration on the largest table in
the database and should be timed and run deliberately rather than folded into an
unrelated fix. `catalog.authors.name_norm` is created with the correct order and
carries a comment pointing here.

### SEC-1 — no request-body size limit on any JSON route
`src/lib/http/api.ts:71` · **major**

`parseBody` does `await request.json()` — the whole body is buffered before Zod
runs. Eleven routes use it. `declaredBodyTooLarge` (`api.ts:100`) exists and is
the prior SEC-3 fix, but it is wired only to the three *multipart* routes. There
is no `middleware.ts`, no route-segment body config, and
`serverActions.bodySizeLimit` does not apply to route handlers — the code's own
comment at `api.ts:92` says so. **Verified:** only
`users/[userId]/avatar`, `fictional-worlds/[worldId]/upload` and
`import/goodreads` call it.

One signed-in reader opening 20 concurrent `POST /api/reviews` at 200 MB each
buffers 4 GB into the heap and the container is OOM-killed. `/api/reviews` has
no rate limit either. `shelves`, `progress`, `works/*/locations`,
`authors/*/locations`, `fictional-worlds`, `users/[userId]` and
`import/rows/*/confirm` are equally exposed.

**Fix:** gate inside `parseBody` — `declaredBodyTooLarge(request, 64 * 1024)`
first, then read via a length-counting stream reader so a chunked body with no
`Content-Length` is bounded too.

### SEC-2 — unrated contribution routes feed five unbounded reads on the public map
writes `src/app/api/works/[workKey]/locations/route.ts:25`,
`src/app/api/authors/[authorName]/locations/route.ts:30`,
`src/app/api/fictional-worlds/route.ts:16` · reads `src/server/map.ts:39`,
`map.ts:72`, `fictional-worlds.ts:84`, `work-locations.ts:31`,
`authors.ts:120` · **major**

**Verified:** none of the five reads has a `take`, and only four routes apply
`checkLimit` — the three contribution routes are not among them. Each accepts a
200-char name and a 10,000-char description. One account can insert millions of
rows; every subsequent load of `/map` — public and anonymous — runs all three
unbounded `findMany`s plus a `getWorksByKeys` hydration over every distinct
`workKey` and serialises the lot into the RSC payload. `GET /api/fictional-worlds`
is public and returns every world with every map.

The prior audit's FLOW-22 fixed this exact shape on the author page via
`AUTHOR_WORKS_LIMIT`. The map was not covered.

**Fix:** `checkLimit` on the three contribution routes; a `take` on all five
reads; bound the map by viewport or paginate.

### SEC-3 — the trusted-hop default is off by one for the documented topology, collapsing every client into one bucket
`src/lib/rate-limit.ts:143`, `:146`, `src/lib/auth/options.ts:51`,
`.env.example:45`, `DEPLOYMENT.md:17-18` · **major**, and a **blocker** if the
live hop count is 2

`.env.example:45` says "1 (the default) is correct behind a single Azure Front
Door". But `DEPLOYMENT.md:17-18` documents Front Door → **Container Apps**, and
Container Apps' own ingress also appends to `X-Forwarded-For`. That is two
appending hops. **Verified:** `clientIpFromHeaders` returns
`chain[chain.length - hops]`, so at `hops = 1` behind two hops it returns Front
Door's egress IP — *identical for every client on the internet*. At `hops = 0`
it falls through to `x-real-ip`, which Container Apps does not set, so every
request keys on the literal string `"unknown"`.

Then `options.ts:51-57`: `authorize()` throws if **either** `login:email:*` or
`login:ip:*` is exhausted, and `checkLimit` records a hit on success as well as
failure. With one shared IP bucket and `LIMITS.login = 10 / 15 min`, **ten
sign-in attempts from one attacker refuse sign-in to every user of the site**
for the window. Forty requests an hour is an indefinite total authentication
outage. Five requests to `register` closes registration site-wide.

This is the mirror of the prior SEC-2: that fix moved the read to the trusted
end of the chain, but the *number* of trusted hops was taken from a topology
description that omits the platform's own ingress.

**Fix:** verify the real chain length against the deployed revision, then set
`TRUSTED_PROXY_HOPS` explicitly and assert it at boot rather than defaulting.
Make an exhausted IP bucket not veto a request whose per-account bucket is
clean. Fail closed instead of sharing one `"unknown"` bucket.

### SEC-4 — targeted account lockout via the per-email login bucket
`src/lib/auth/options.ts:51-57` · **minor**

**Verified:** the limit is checked before the user lookup and bcrypt (correct
for timing) but counts *all* attempts, not just failures, and the victim's own
correct password spends the same bucket. Ten wrong passwords every fifteen
minutes locks a known address out permanently. No CAPTCHA, no unlock, no
notification.

**Fix:** record a hit only on a *failed* attempt; keep a separate higher cap on
total attempts to preserve the anti-stuffing property.

### SEC-5 — LIKE metacharacters unescaped in the search ranking expression
`src/server/catalog.ts:128` · **minor** (hardening)

The prior SEC-14 escaped `%`, `_` and `\` on the import path and documented why
ten lines away (`catalog.ts:535-543`); the search path did not get the same
treatment. A query containing `%` or `_` awards the `W_PREFIX` +20 bonus to rows
that do not prefix-match, distorting order. **Not** a scan risk — the `WHERE`
clause at `:136-137` is independent, so the LIKE only evaluates against rows
already matched. Reported because the asymmetry will read as an oversight.

**Fix:** escape `[\\%_]` when building `norm`, as `:543` already does.

### SEC-6 — no delete path for a fictional world, anywhere in the API
`src/app/api/fictional-worlds/route.ts:16` · **minor**

POST exists; no DELETE handler in any of the 23 route files. Unrated, no dedupe,
arbitrary 200-char names, and the public GET renders them on the map. The spam
is permanent and irreversible through the API — a database operator must
intervene. The prior SEC-7 added uploader-or-moderator deletion for maps and
both location types and stopped short of worlds.

**Fix:** `DELETE /api/fictional-worlds/[worldId]` restricted to a moderator, and
rate-limit the POST.

### SEC-7 — the community-edit PATCH is unrated site-wide vandalism
`src/app/api/fictional-worlds/maps/[mapId]/route.ts:54` · **minor**

Community editing is deliberate policy (comment at `:12-16`) and is not
contested. The defect is that it is unrated: one account can walk every `mapId`
and rewrite every title and description on the site in one loop. `updateMap`
records `updatedById` but nothing surfaces it and nothing reverts it.

**Fix:** rate-limit the PATCH per account; surface `updatedById`; keep prior
versions so an edit can be reverted.

### SEC-8 — the in-memory limiter is documented as wrong for the target, and nothing enforces the stated mitigation
`src/lib/rate-limit.ts:13-23`, `DEPLOYMENT.md:397-406` · **minor**

Honestly documented, so not a discovery — but it is a live security control that
does not hold where the app runs, and the stated mitigation ("pin to one
replica, or move the limiter to a shared store") is enforced by nothing in CI
and is not among `deploy:verify`'s checks. Effective limits become
`limit x replicas`, and Container Apps adds replicas under exactly the load an
attacker generates, so the limits loosen when they are needed most. Interacts
with SEC-3: on a scaled revision both readings are live on different replicas.

**Fix:** a `deploy:verify` check asserting either `maxReplicas == 1` or a
configured shared limiter store, so the deployment cannot silently drift.

### SEC-9 — dead module interpolates unvalidated input into a fetch URL
`src/lib/sources/openlibrary.ts:27` · **minor** (hardening, not reachable)

The only SSRF-shaped code in the repo, and **not reachable** — zero importers of
`sources/openlibrary`, `searchBooks` or `getBookByISBN` outside the file. Path
interpolation cannot change the host, so even if wired it would not be
host-controlled. Reported because the import route's header comment describes
removing exactly this per-book HTTP call, and the module it replaced is still
sitting there ready to be re-imported.

**Action: RECORD AND LEAVE.** The agent recommended deleting it. The standing
rule forbids that — no test or spec line covers its behaviour.

## Spec conformance (10 findings, 1 open question)

### SPEC-1 — the most load-bearing invariant in the schema has no mechanical guard
`scripts/deploy/verify.ts:272-303` and the absence of any test · **major**

`ARCHITECTURE.md:40-42`: "**Nothing in `app` may hold a foreign key into
`catalog`.** A bad ingest would cascade into user data." `STATUS.md:34-37` calls
it "the single most load-bearing decision in the schema".

The invariant **holds** — all FK constraints targeting `catalog` originate in
`catalog`. But nothing guards it. No test queries `pg_constraint`, and
`deploy:verify` asserts extensions, migrations, `work_mem`, four indexes, the
trigger and statistics — never a constraint. Every *other* named invariant has a
named guard (exclusive shelves, `timestamptz`, search indexes, route
conventions). Adding `work CatalogWork @relation(...)` to `ShelfItem` would
generate a migration and leave every suite green. The prior audit verified this
*by hand*, which is the evidence that it is a manual check.

**Fix:** an integration test asserting the set is empty —
`SELECT conname FROM pg_constraint c JOIN pg_class r ON r.oid=c.conrelid JOIN pg_namespace rn ON rn.oid=r.relnamespace JOIN pg_class f ON f.oid=c.confrelid JOIN pg_namespace fn ON fn.oid=f.relnamespace WHERE c.contype='f' AND rn.nspname='app' AND fn.nspname='catalog'`
— mirrored as a `deploy:verify` check so a restore that added one is caught at
release.

### SPEC-3 — CC BY-SA is asserted over readers' own data

### FLOW-10 — every imported book is recorded as finished *today*; the parsed date is used only as a boolean
`src/lib/sources/goodreads.ts:189` → `src/server/imports.ts:390-396` →
`src/server/progress.ts:188-225` → `src/server/wrapped.ts:56-58` · **BLOCKER**

`imports.ts:390` reads `if (row.dateRead && row.exclusiveShelf === "read")` —

`finishReading` takes no date and stamps `new Date()`. The UI promises the

shelves, and **reading dates** will be imported."

A 300-book export spanning 2010–2024 makes `/wrapped` for the current year
